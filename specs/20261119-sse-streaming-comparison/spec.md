# Feature Specification: Kotlin POST SSE 스트리밍 구현 방식별 비교 및 성능 벤치마크

**Feature Directory**: `specs/20261119-sse-streaming-comparison`  
**Created**: 2026-11-19  
**Status**: Draft  
**Input**: Kotlin SSE 스트리밍 구현 방법별(Spring MVC, WebFlux, Coroutine Flow, Virtual Thread, SseEmitter)로 데모를 만들어 비교한다. 실서비스에서 사용 가능한 조합을 선정하고, 조합별로 동일한 기능(POST SSE)을 구현해 성능을 비교한다. (`sse-compare`)

## Clarifications

### Session 2026-11-19

- Q: MVC + Flow 조합(C)에서 코루틴 디스패처를 몇 가지로 비교할까? → A: `Default`와 Virtual Thread 디스패처 2개 변형(C1, C2)으로 비교한다. 조합 F는 별도 조합으로 두지 않고 C 변형으로 흡수한다.
- Q: 한계 연결 수는 어떤 기준으로 판정할까? → A: 에러율 1% 초과 또는 이벤트 간 지연 p99가 설정 간격(`intervalMs`)의 2배를 넘는 최초 단계.
- Q: 벤치마크는 어디에서 실행할까? → A: 로컬 Docker(리소스 제한)를 기본으로 하고 Linux 재실행은 선택. 스크립트는 환경에 독립적으로 작성한다.
- Q: 부하 생성 클라이언트는 무엇으로 할까? → A: Kotlin 코루틴 커스텀 클라이언트를 주 부하기로 쓰고 k6는 교차 검증용 보조로 둔다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 동일 계약의 POST SSE 엔드포인트를 조합별로 제공 (Priority: P1)

개발자는 서로 다른 구현 조합(서버 스택, 동시성 모델, 반환 타입)이 **완전히 동일한 외부 계약**의 POST SSE 엔드포인트를 제공하는 것을 확인할 수 있어야 한다. 그래야 조합 간 차이가 스펙 해석 차이가 아니라 구현 방식 차이로만 나타난다.

**Why this priority**: 공정한 비교의 전제 조건이다. 계약이 일치하지 않으면 이후 성능 비교는 의미가 없다.

**Independent Test**: 각 조합을 단독으로 기동하고, 동일한 요청을 보내 이벤트 순서, 이벤트 타입, 종료 동작이 모든 조합에서 같은지 공통 계약 테스트로 검증한다.

**Acceptance Scenarios**:

1. **Given** 임의의 조합이 기동된 상태, **When** 클라이언트가 `POST /chat/stream`에 `{prompt, events, intervalMs}`를 보내면, **Then** 서버는 `Content-Type: text/event-stream`으로 `message` 이벤트를 `events`개, `intervalMs` 간격으로 순서대로 전송하고 마지막에 `done` 이벤트를 보낸 뒤 스트림을 종료한다.
2. **Given** 스트리밍 진행 중, **When** 클라이언트가 연결을 끊으면, **Then** 서버는 해당 스트림의 작업을 중단하고 리소스를 정리한다.
3. **Given** 잘못된 요청 본문(예: `events` 음수, 필수 필드 누락), **When** 요청을 보내면, **Then** 스트림을 시작하지 않고 모든 조합이 동일한 오류 응답을 반환한다.
4. **Given** 장시간 스트림, **When** 이벤트 간격이 길면, **Then** 서버는 연결 유지를 위한 heartbeat를 일정 주기로 보낸다.

### User Story 2 - 순수 스트리밍 성능 비교 (DB 없음) (Priority: P1)

개발자는 DB 같은 외부 의존 없이 지연(sleep/delay)만으로 스트림을 만들어 조합별 **연결 확장성과 이벤트 전달 지연**을 비교할 수 있어야 한다.

**Why this priority**: 스트리밍 모델 자체의 차이(스레드, 메모리, 지연)를 잡음 없이 보여주는 핵심 비교다.

**Independent Test**: 조합 하나를 고정된 리소스 제한으로 띄우고, 동시 연결 수를 단계적으로 늘리는 부하를 가해 지표를 수집한다. 조합별로 반복해 결과 표를 만든다.

**Acceptance Scenarios**:

1. **Given** 모든 조합이 동일한 리소스 제한과 동일한 JVM 설정으로 기동, **When** 동시 연결 수를 100 → 1,000 → 5,000 → 10,000으로 단계별 증가시키면, **Then** 단계마다 TTFB, 이벤트 간 지연(p50/p95/p99), 에러율, 활성 스레드 수, 메모리 사용량이 기록된다.
2. **Given** 짧은 스트림(이벤트 10개)을 고정 도착률로 요청, **When** 일정 시간 지속, **Then** 처리량(스트림/초, 이벤트/초)과 완료율이 기록된다.
3. **Given** 부하 실행이 끝난 상태, **When** 결과를 집계하면, **Then** 조합별 비교표와 한계 연결 수(에러율이 기준을 넘는 지점)가 산출된다.

### User Story 3 - 블로킹 DB 저장을 포함한 성능 비교 (Priority: P2)

개발자는 스트림 시작 시 사용자 메시지를, 종료 시 완성된 응답을 RDB에 저장하는 **현실적인 시나리오**에서 조합별 차이를 비교할 수 있어야 한다. 블로킹 I/O를 만났을 때 각 조합이 어떻게 동작하는지가 핵심이다.

**Why this priority**: 실서비스에는 거의 항상 블로킹 저장이 있어 순수 스트리밍 결과만으로는 선택하기 어렵다. 다만 US1, US2 이후 추가해도 가치가 독립적이다.

**Independent Test**: DB 저장 옵션을 켠 상태로 US2와 같은 부하를 실행하고, DB 없는 결과와 비교한다.

**Acceptance Scenarios**:

1. **Given** DB 저장이 활성화된 조합, **When** 스트림을 요청하면, **Then** 시작 시 요청 메시지가, 종료 시 응답 전체가 저장되고 저장된 건수가 요청 수와 일치한다.
2. **Given** 논블로킹 스택(WebFlux)의 DB 접근, **When** 블로킹 저장을 이벤트 루프에서 직접 호출하지 않고 격리된 실행 환경 또는 논블로킹 드라이버로 처리하면, **Then** 이벤트 지연이 악화되지 않는다. 두 방식의 결과가 각각 기록된다.
3. **Given** 연결 수가 DB 커넥션 풀 크기를 크게 초과, **When** 부하가 지속되면, **Then** 커넥션 획득 대기 시간과 풀 사용량이 기록되어 병목 위치를 확인할 수 있다.

---

### User Story 4 - 안정성·장애 시나리오 비교 (Priority: P3)

개발자는 **장시간 유지, 클라이언트 중도 이탈, 느린 클라이언트** 상황에서 조합별 리소스 누수와 백프레셔 처리 차이를 확인할 수 있어야 한다.

**Why this priority**: 실서비스 선택 시 중요하지만, 기본 확장성 비교(US2, US3)가 먼저다.

**Independent Test**: 고정 연결 수로 수 분간 유지하며 메모리 추이를 관찰하고, 임의로 연결을 끊거나 읽기 속도를 제한해 서버 상태를 확인한다.

**Acceptance Scenarios**:

1. **Given** 고정 수의 장시간 연결, **When** 일정 시간 유지하면, **Then** 메모리와 스레드 수가 지속 증가하지 않는다(누수 없음).
2. **Given** 연결의 일정 비율이 임의 시점에 끊김, **When** 부하가 지속되면, **Then** 끊긴 스트림의 서버 작업이 정리되고 활성 연결 수 지표가 실제와 일치한다.
3. **Given** 수신 속도가 느린 클라이언트, **When** 스트림을 전송하면, **Then** 서버 메모리가 무한히 증가하지 않고, 타임아웃 또는 정리 동작이 일관되게 일어난다.

---

### User Story 5 - 결과 보고서와 실서비스 조합 추천 (Priority: P2)

개발자는 모든 측정 결과를 한 문서에서 비교하고, 워크로드 유형별 **추천 조합과 근거**를 얻을 수 있어야 한다.

**Why this priority**: 비교의 최종 산출물이며 의사결정에 직접 쓰인다.

**Independent Test**: 결과 문서만 읽고 "블로킹 기반 기존 서비스", "신규 I/O 위주 서비스" 각각에 어떤 조합을 선택할지 근거와 함께 답할 수 있어야 한다.

**Acceptance Scenarios**:

1. **Given** 모든 시나리오의 측정 결과, **When** 보고서를 생성하면, **Then** 조합 × 시나리오 × 지표 비교표와 그래프가 포함된다.
2. **Given** 보고서, **When** 워크로드 유형별 추천 섹션을 보면, **Then** 각 추천에 측정 근거(수치)와 트레이드오프(코드 복잡도, 마이그레이션 비용)가 명시된다.
3. **Given** 동일 조건으로 재실행, **When** 실행 스크립트를 쓰면, **Then** 한 명령으로 조합과 시나리오를 지정해 재현할 수 있다.

### Edge Cases

- 클라이언트 끊김과 서버 정상 종료가 동시에 일어나면? → 취소를 우선하며 오류 없이 종료하고, 활성 연결 지표는 정확히 한 번만 감소한다.
- `events`가 0이거나 매우 큰 값(예: 1,000,000), `intervalMs`가 범위 밖인 경우는? → 허용 범위(`events` 1~100,000, `intervalMs` 0~60,000)를 벗어나면 400으로 거부한다. `intervalMs`=0은 허용한다.
- 업스트림(이벤트 생성) 처리 중 예외가 발생하면? → `error` 이벤트를 보낸 뒤 스트림을 정상 종료한다(연결을 끊지 않는다).
- DB 저장 실패 시? → 시작 시 저장 실패는 `error` 이벤트(`DB_ERROR`) 후 종료한다. 종료 시 저장 실패는 이미 `done`이 전송된 뒤이므로 스트림은 정상 완료로 보고 로그와 실패 카운터 지표만 남긴다.
- DB 커넥션 풀이 고갈되면? → 획득 대기 타임아웃(기본 5초) 후 `error` 이벤트(`DB_TIMEOUT`)로 종료하며, 대기 시간은 지표로 기록한다.
- 부하기 자체가 병목(CPU, 파일 디스크립터, 포트 고갈)이 되어 서버 한계로 오해될 수 있는가?
- 리버스 프록시나 로드밸런서가 SSE를 버퍼링하는 경우(범위 밖이지만 문서에 주의사항으로 기록)

## Requirements *(mandatory)*

### Functional Requirements

**API 계약**

- **FR-001**: 모든 구성은 `POST /chat/stream`을 제공해야 하며, 요청 본문은 `prompt`(문자열), `events`(전송할 이벤트 수), `intervalMs`(이벤트 간격 ms)를 필수로, `persist`(요청 단위 DB 저장 여부, 기본 false)와 `failAt`(테스트·벤치마크 전용 오류 유발 위치, 선택)를 선택 필드로 포함해야 한다.
- **FR-002**: 응답은 `text/event-stream`이며 `message` 이벤트 N개(순번 포함)와 마지막 `done` 이벤트로 구성되어야 한다.
- **FR-003**: 처리 중 오류가 발생하면 `error` 이벤트를 전송한 뒤 스트림을 종료해야 한다. 모든 구성에서 동일해야 한다. 오류는 요청의 `failAt`(1-based 이벤트 순번)이 지정되면 해당 순번 직전에 의도적으로 발생시켜 검증할 수 있어야 한다.
- **FR-004**: 시스템은 설정 가능한 주기로 heartbeat(SSE 주석 행 `: ping`)를 전송해야 한다.
- **FR-005**: 클라이언트 연결 종료를 감지하면 해당 스트림의 작업을 취소하고 리소스를 해제해야 한다.
- **FR-006**: 잘못된 요청은 스트림 시작 전에 동일한 오류 코드와 형식으로 거부해야 한다.
- **FR-007**: 기준선으로 같은 핸들러를 쓰는 `GET /stream`(쿼리 파라미터 입력)을 제공해 POST 바디 처리 비용을 분리 측정할 수 있어야 한다.

**조합 구성**

- **FR-008**: 다음 구성을 각각 독립적으로 실행 가능해야 한다(모듈 또는 같은 모듈의 프로파일로 제공).
  - A: Spring MVC + `SseEmitter` + 플랫폼 스레드 풀
  - B: Spring MVC + `SseEmitter` + Virtual Thread
  - C1: Spring MVC + Kotlin Coroutine `Flow` (`Dispatchers.Default`)
  - C2: Spring MVC + Kotlin Coroutine `Flow` (Virtual Thread 디스패처)
  - D: Spring WebFlux + Reactor `Flux`
  - E: Spring WebFlux + Kotlin Coroutine `Flow` (`suspend`)
- **FR-009**: 조합 간 공통 요소(요청/응답 모델, 이벤트 생성 규칙, 계약 테스트)는 공유 모듈에 두어야 한다.
- **FR-010**: 이벤트 지연은 블로킹 스택에서는 스레드 sleep, 논블로킹 스택에서는 논블로킹 delay로 구현하되 동일한 시간 의미를 가져야 한다.

**DB 시나리오**

- **FR-011**: 각 구성은 실행 프로파일로 DB 저장 기능을 활성화할 수 있어야 한다. 활성화된 경우 요청의 `persist=true`인 스트림만 시작 시 요청 메시지, 종료 시 응답 전체를 저장한다. DB 프로파일이 없으면 `persist`는 무시한다.
- **FR-012**: MVC 계열(A, B, C1, C2)은 블로킹 DB 접근을 사용해야 한다.
- **FR-013**: WebFlux 계열(D, E)은 (1) 블로킹 DB 접근을 격리된 실행 환경에서 호출하는 방식과 (2) 논블로킹 DB 드라이버 방식을 모두 제공해 비교할 수 있어야 한다.
- **FR-014**: DB 커넥션 풀 크기는 모든 조합에서 동일하게 설정하고 결과 보고서에 명시해야 한다.

**성능 측정**

- **FR-015**: 부하 시나리오 S1(동시 연결 단계 증가), S2(짧은 스트림 고정 도착률), S3(장시간 유지), S4(DB 포함), S5(중도 이탈), S6(느린 클라이언트)를 정의하고 실행할 수 있어야 한다.
- **FR-016**: 클라이언트는 POST SSE의 TTFB와 이벤트별 수신 시각을 측정할 수 있어야 한다. 주 부하기는 Kotlin 코루틴 클라이언트이며, k6는 교차 검증용 보조 도구로 사용한다.
- **FR-017**: 서버 지표(활성 연결 수, 스레드 수, CPU, 힙/RSS, GC pause, DB 커넥션 풀 상태)를 수집하고 시각화해야 한다.
- **FR-018**: 모든 조합은 동일한 CPU/메모리 제한, 동일한 JVM 설정, 동일한 페이로드로 한 번에 하나씩 순차 측정해야 한다. 실행 환경은 로컬 Docker를 기본으로 하며 스크립트는 환경 독립적이어야 한다. 워밍업 후 측정하며 조합당 3회 이상 반복한다.
- **FR-019**: 하나의 명령으로 조합과 시나리오를 지정해 벤치마크를 실행하고 결과를 파일로 저장할 수 있어야 한다.
- **FR-020**: 결과 보고서는 조합 × 시나리오 × 지표 비교표, 한계 연결 수, 워크로드별 추천과 근거를 포함해야 한다.

**검증**

- **FR-021**: 공통 계약 테스트는 모든 조합에 동일하게 실행되어야 하며, 통합 테스트는 Testcontainers로 DB를 구성해야 한다.

### Key Entities

- **StreamRequest**: 스트림 요청. `prompt`, `events`, `intervalMs`, 선택적으로 `persist`(DB 저장 여부), `failAt`(오류 유발 위치).
- **StreamEvent**: 전송 이벤트. 타입(`message`, `done`, `error`, heartbeat), 순번, 내용, 서버 전송 시각.
- **Combination**: 비교 대상 구현 구성. 식별자(A, B, C1, C2, D, E), 서버 스택, 동시성 모델, 반환 타입, DB 접근 방식.
- **Scenario**: 부하 시나리오. 식별자(S1~S6), 동시 연결 수, 이벤트 수/간격, 지속 시간, DB 포함 여부.
- **BenchmarkResult**: 조합 × 시나리오 측정 결과. 클라이언트 지표(TTFB, 이벤트 지연 분포, 에러율, 처리량), 서버 지표(스레드, CPU, 메모리, GC, 풀 상태).
- **ChatMessage**: DB 저장 대상. 요청 메시지와 응답 전체, 생성 시각, 스트림 식별자.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 6개 구성(A, B, C1, C2, D, E) 모두 동일한 공통 계약 테스트를 100% 통과한다.
- **SC-002**: 각 조합에 대해 시나리오 S1과 S2의 결과를 지표 전체(TTFB, 이벤트 지연 p50/p95/p99, 에러율, 스레드 수, 메모리)와 함께 확보한다.
- **SC-003**: 각 조합의 한계 연결 수(에러율 1% 초과 또는 이벤트 간 지연 p99가 설정 간격의 2배를 넘는 최초 단계)가 식별된다.
- **SC-004**: 같은 조합을 같은 조건으로 3회 반복했을 때 핵심 지표(p95 지연, 처리량)의 편차가 ±15% 이내로 재현된다. 초과 시 원인이 보고서에 기록된다.
- **SC-005**: DB 포함 시나리오에서 DB 없는 결과 대비 조합별 성능 저하율이 수치로 제시되고, 병목 위치(스레드 풀, 커넥션 풀, 이벤트 루프)가 설명된다.
- **SC-006**: 중도 이탈 시나리오 종료 후 모든 조합에서 활성 연결 수와 스레드 수가 부하 시작 전 수준으로 복귀한다.
- **SC-007**: 하나의 명령으로 임의의 조합·시나리오 벤치마크를 실행하고 결과 파일이 생성된다.
- **SC-008**: 보고서를 읽은 개발자가 "기존 블로킹 서비스"와 "신규 I/O 중심 서비스" 각각에 대해 추천 조합을 근거와 함께 선택할 수 있다.

## Assumptions

- **대상 사용자**: Kotlin/Spring에 익숙한 개발자가 실서비스 도입 판단을 위해 비교한다.
- **런타임**: Java 21(Virtual Thread 사용), Spring Boot 3.x, Kotlin, Gradle Kotlin DSL을 기준으로 한다. 프로젝트 규칙에 따라 로깅은 `kotlin-logging`, 테스트는 Kotest를 사용한다.
- **위치**: 저장소 루트의 새 멀티모듈 프로젝트 `sse-compare/`로 구성한다(기존 `http-streaming/sse`와 별개). 조사 문서는 `sse-compare/docs/research/`에 둔다.
- **실제 LLM 연동 없음**: 이벤트는 합성 데이터를 지연 간격으로 생성해 업스트림을 시뮬레이션한다.
- **인증, 프런트엔드 UI, 리버스 프록시/로드밸런서 튜닝은 범위 밖**이다. 프록시 버퍼링 주의사항만 문서에 기록한다.
- **실행 환경**: 로컬 Docker(컨테이너 리소스 제한)를 기본으로 하며, 결과는 절대 성능이 아닌 **상대 비교용**으로 해석한다. 필요하면 Linux 환경에서 재실행한다.
- **부하 도구와 모니터링**: Kotlin 코루틴 클라이언트(주), k6(보조), Prometheus, Grafana를 사용한다.
- **DB**: MySQL을 기본으로 하며, 테스트에는 Testcontainers를 사용한다.
- **제외한 조합**: WebFlux + Virtual Thread(이벤트 루프 모델과 맞지 않음), 순수 `StreamingResponseBody`(SSE 포맷 지원 약함), Ktor(범위 확장 시 후속).
