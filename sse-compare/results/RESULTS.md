| 항목 | 설정값 |
|------|--------|
| 런타임 | Java 21, Kotlin 1.9.25, Spring Boot 3.4.4 |
| 컨테이너 제한 | `cpus: 2.0`, `memory: 1g` |
| JVM 옵션 | `-Xmx512m -Xms512m -XX:+UseG1GC` |
| Tomcat 설정 (MVC) | `threads.max: 200`, `max-connections: 20000`, `accept-count: 1000` |
| DB 커넥션 풀 (S4) | HikariCP `maximum-pool-size: 10`, R2DBC `max-size: 10` (획득 타임아웃 5s) |
| 한계 판정 기준 (SC-003) | 에러율 > 1% 또는 이벤트 간 지연 p99 > 2 × `intervalMs` |
| 해석 주의 | 로컬 macOS Docker Desktop 결과는 절대 수치가 아닌 **구성 간 상대 비교용** |

## 3. 워크로드별 실서비스 추천 (SC-008)

| 워크로드 유형 | 추천 구성 | 근거 및 트레이드오프 |
|---------------|-----------|----------------------|
| **기존 MVC + JPA 블로킹 서비스** | **B (MVC + SseEmitter + Virtual Thread)** | `spring.threads.virtual.enabled=true` 설정만으로 플랫폼 스레드 200개 한계를 돌파한다. 코드 변경·마이그레이션 비용이 가장 낮으며, DB 병목은 HikariCP 풀 크기로 명확히 통제된다. |
| **신규 I/O 중심 서비스 (LLM 프록시 등)** | **E (WebFlux + Coroutine Flow)** | Netty 논블로킹 이벤트 루프와 Kotlin `suspend`/`Flow` 조합으로 연결당 메모리와 스레드 오버헤드가 가장 적고, 느린 클라이언트 백프레셔가 자연스럽다. 단, 블로킹 라이브러리 혼용 시 격리(`Dispatchers.IO`) 또는 R2DBC 전환이 필요하다. |
| **MVC 유지 + 코루틴 스트림 문법 선호** | **C2 (MVC + Flow + VT Dispatcher)** | 기존 서블릿 필터/보안/JPA 생태계를 유지하면서 코루틴 `Flow` 문법을 쓸 수 있다. 다만 쓰기 시점에는 서블릿 스레드를 거치므로 초대규모 동시 연결에서는 WebFlux(E)보다 불리하다. |
| **팀이 Reactor에 익숙한 리액티브 서비스** | **D (WebFlux + Reactor Flux)** | E와 동등한 Netty 논블로킹 확장성을 제공하지만, 코루틴 대비 코드 가독성과 디버깅 학습 비용이 높다. |
